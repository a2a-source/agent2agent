# Wallet reservations

`WalletReservations` is an internal SQLite library for excluding actual token units from competing investment tasks. It is not yet wired into the Scheduler or Journal signing path. It does not fetch balances, authorize a trade, reserve funds onchain, verify live receipts, or replace quote/eligibility checks.

`reserve({id, planId, transactionIds, amounts}, now)` requires a stored READY stable wallet plan, a successful committee-verified consumption reference, and a fresh completed portfolio snapshot. Amounts are positive integer strings in native/token base units, keyed by `native` or token address. Quantities must fit snapshot balances after recorded reservations and the protected gas floor. The caller must include the entire maximum spend and additional transaction gas budget; the library cannot infer a swap from those amounts.

One reservation bundle is active per chain/wallet. Repeating the identical reservation ID returns its historical record, including after terminal transitions; this is not fresh signing authorization. Conflicting contents fail. Transaction IDs cannot be reused across reservations. Pending local Journal entries, active signer leases and known finalized transactions later than the input snapshot block prevent new reservations.

`cancel(id, now)` only releases an unsigned bundle: none of its predetermined Journal IDs may exist and the wallet signer lease must be inactive. This covers a signer that has acquired its lease but has not yet persisted transaction bytes. The future execution adapter must check active reservation ownership inside the same transaction/lease protocol before signing; this library alone cannot stop an unrelated spender.

`settle(id, snapshotId, now)` requires every predetermined Journal ID to have a stored confirmed success and no active wallet signer lease, plus a fresh completed balance snapshot at or after all receipt blocks. Same-height block hashes must agree. The reservation is closed, and later reservations must use a snapshot block newer than this settlement boundary. Expected sale proceeds are never credited by this module. Reverted transactions remain reserved because Journal can retry a reverted ID; they are not terminal execution outcomes. Bundles with partially prepared transaction sequences also remain reserved; the execution adapter must implement explicit safe abandonment/reconciliation of unused steps before this library can support that case.

Records are `wallet-reservation` and `wallet-reservation-boundary`, with changes retained in the normal SQLite history. Current validation trusts canonical receipt state maintained by Journal and confirmed snapshots maintained by the collector. Live reorg/nonce reconciliation, chain validation of signed bytes, fixed route and recipient verification, risk limits, classified flows and actual execution orchestration remain integration work.
