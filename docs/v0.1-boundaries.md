# v0.1 operating boundaries

This document defines the implemented economic and custody boundaries before QSP consumption and investment execution. See [protocol behavior](protocol.md) for elections, confirmation, cadence and isolation, and [usage](usage.md) for configuration and API details.

## Compute billing

Each dispatched physical LLM completion request costs **US$0.01**, converted to BNB using the request-time onchain BNB/USD quote and rounded up to a whole wei. This is a platform request fee, independent of provider usage fields or the provider's invoice. A role's ReAct loop can make multiple requests; each dispatched request is charged separately. Provider errors, malformed output and rate-limit retries do not undo a dispatched request fee. Cache hits, pre-dispatch rejection/cancellation and committee signature checks do not add a completion charge.

Receipts persist the pricing quote, request identity and exact debit. An uncertain process crash after the durable dispatch commitment is conservatively charged once and is not blindly replayed. Previously settled requests cannot be repriced through reconciliation. Legacy unknown holds retain their existing reconciliation path. Each Agent has its own compute ledger; the guarantee and investment principal do not fund a compute shortfall automatically.

The platform's compute share of tax revenue supplies credits; authenticated administrative credits remain available for controlled operation/testing. This release adds no user recharge product, automatic refund policy or online fee-change API. A future change to billing or refunds requires an explicit policy and accounting migration.

## Custody and user authority

Users authenticate with their own credentials and may access or operate their own Agents. Administrative routes use separate operator authentication. An Agent has its own BSC wallet, encrypted at rest with the configured RSA key and decrypted for runtime signing; the platform remains the custodian of these keys. Independent Agent reasoning and signatures do not imply independent key custody.

The existing user routes support token launch and bonded-guarantee exit/withdrawal. Guarantee withdrawal returns funds to the Agent wallet; it is not a withdrawal to an arbitrary user-selected recipient. This release exposes no private-key export, arbitrary investment-wallet transfer, trading, QSP execution or profit-distribution endpoint. These capabilities require the next-stage custody, authorization and risk design.

## Funds and deployment defaults

| Rule | v0.1 behavior |
| --- | --- |
| Token tax | Launch requests specify 3% buy and 3% sell tax through the Flap adapter. |
| Received tax revenue | 30% goes to the platform: 15% compute allocation and the remaining platform share for operations; 70% goes to the Agent. Integer rounding follows the splitter contract. |
| Worker guarantee | At least 0.3 BNB effectively bonded in the staking contract, separately from spendable investment principal. Extra stake does not increase new-term election priority. |
| Automatic top-up | Confirmed Agent-wallet funds from any source can top up the guarantee, after pending-spend and gas reservations. Exactly 0.3 BNB in the wallet is insufficient if staking gas must also be paid. |
| Exit request | Disables automatic top-up immediately. Onchain exit removes effective bonded qualification and starts the deployed lock period. |
| Standard deployment delay | Seven days (`7 * 86400` seconds). Shorter local/testnet verification contracts do not change the standard deployment helper. |
| Agent transaction gas | The Agent wallet pays its staking/exit/withdrawal transactions. The default native reserve is 0.001 BNB (`chain.gasReserveWei`). |
| Launch transaction funding | The configured operator signer funds launch transactions. Default attached native value is 0.001 BNB (`chain.launchValueWei`), separate from transaction gas. This configuration value is not a guaranteed external protocol fee. |
| Requested tax duration | Default `315360000` seconds (`chain.taxDuration`); actual support and execution depend on the configured Flap deployment. |
| Chain writes | Disabled by default; the supplied chain default is BSC testnet. |

Defaults remain configurable where supported. Live deployment requires the actual contract addresses, permissions and sufficient signer funds; configuration does not establish that a third-party protocol accepts a particular fee or duration. This release does not introduce user reimbursement or launch-cost settlement rules.

## Verification scope and next stage

Automated coverage includes fixed-request billing and replay protection, authenticated ownership, tax splitting, staking and delayed owner withdrawal, external-wallet funding and autonomous top-up, committee confirmation, deterministic fair election, five-minute end-relative scheduling, and operational/security isolation. Local EVM tests and clock-controlled scheduling tests are simulations; they are not new live mainnet acceptance runs.

Previously recorded limits remain: the post-DEX-migration tax-settlement path has not been fully accepted; C4 research has met its prototype quality threshold but retains narrative inaccuracies and unstable news-body coverage. A signed, committee-confirmed QSP is still a research proposal with `executed: false`, not an order, fill, guarantee of research truth or investment return.

The next stage is the design of QSP consumption and Agent-wallet investment. It must define execution authorization, fresh-price/route checks, portfolio reconciliation, idempotent order handling and failure recovery before enabling transfers or trades. Profit distribution remains separately scoped.
